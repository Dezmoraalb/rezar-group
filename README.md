# Rezar Group — демо сайту «Авто в наявності»

Робочий демо-концепт сайту Rezar Group від студії WebEngine (webengine.studio), зроблений за технічним завданням
«Авто в наявності», версія 1.0 від 29.10.2026. Це не макет: фільтри, нескінченна прокрутка, картка авто, архів
проданих і «Схожі автомобілі» працюють так, як вимагає ТЗ. Дані поки що моковані: 1200 авто, детерміновано
згенерованих скриптом. Фронтенд звертається до них через модуль `src/lib/api.js`, який має ту саму форму, що й
майбутній бекенд Rezar. Коли бекенд з'явиться, код сторінок не зміниться, зміниться тільки реалізація цього модуля.

* Мова сайту — українська. Ціни показуються тільки в доларах США, тільки підсумкові (ціна API + 500 USD).
* Контакти Rezar (телефон, Telegram, адреса, e-mail) поки що заглушки. Кожен такий елемент має атрибут
  `data-placeholder`, а замінюються вони в одному місці: `src/lib/contacts.js` + `src/partials/*.html`.
* Постачальник і будь-які контрагенти на сайті не згадуються ніде: ні в тексті, ні в alt, ні в посиланнях.
* Фото авто в демо взяті з Unsplash (ліцензія Unsplash). У продакшені це будуть власні фото Rezar з Cloudflare R2.

## Запуск

Потрібен Node.js 20+ (CI використовує 22).

```bash
npm ci
npm run dev        # http://localhost:5173/rezar-group/        — розробка з hot reload
npm run build      # збірка в dist/
npm run preview    # http://localhost:4173/rezar-group/        — перевірка production-збірки
npm run check      # перевірки логіки: час публікації (§9), похожі (§16), фільтри/сортування/пагінація, дані
npm run gen:data   # перегенерувати мок-дані (детерміновано; `npm run gen:data -- --verify` ще й перевіряє, що всі фото віддають HTTP 200)
```

**Деплой.** Сайт статичний. На GitHub Pages він публікується під підшляхом `/rezar-group/`: при push у `main`
workflow `.github/workflows/deploy.yml` виконує `npm ci → npm run check → npm run build` і викладає `dist/`.
Для власного домену в корені збирайте з `BASE=/ npm run build`. Усі внутрішні посилання враховують base: у HTML через
`%BASE%`, у JS через `src/lib/env.js`. Картка авто відкривається через query-рядок (`car/?id=10533`), тому окремих
HTML-файлів на кожне авто не потрібно.

**Демо-перемикачі в URL** (для показу та тестування):

| параметр | що робить |
|---|---|
| `?sync=stale` | імітує недоступність API постачальника: остання успішна синхронізація була 36 год тому. Сайт працює далі з власних даних і пише «Дані станом на …», а наявність не подає як підтверджену (§3, §14). Діє до кінця сесії вкладки; `?sync=ok` вимикає |
| `?now=2026-10-29T12:00:00Z` | фіксує «поточний» час (зручно перевіряти правила §9 і «Нові надходження») |
| `?rebase=0` | показує дати з даних як є. За замовчуванням вони зсуваються на реальний годинник цілими слотами синхронізації, щоб «N годин тому» і «Нові надходження» завжди виглядали свіжими |
| `?state=error` (каталог) | один раз показує стан помилки завантаження; кнопка «Спробувати ще» після цього працює |
| `?tier=low\|mid\|high` | примусовий рівень анімацій (за замовчуванням визначається за пристроєм) |

## Сторінки

| адреса | що там |
|---|---|
| `/rezar-group/` | **Головна** (§12): про компанію, нові надходження з каталогу наживо, переваги, шість етапів замовлення, юридичні гарантії, відгуки, місцезнаходження з картою та корпоративні контакти, фінальний заклик до дії |
| `/rezar-group/catalog/` | **Каталог** (§7–10): «Розділ» (усі / нові надходження / в наявності / в дорозі / продано), фільтри, сортування, нескінченна прокрутка по 24 |
| `/rezar-group/catalog/?section=sold` | **Архів проданих** (§4): фото, характеристики, ціна продажу; фільтри працюють і тут |
| `/rezar-group/catalog/?fav=1` | **Обрані** (сердечко на фото; зберігаються в браузері) |
| `/rezar-group/car/?id=…` | **Картка авто** (§11): галерея, характеристики, VIN з копіюванням, опис, комплектація, кнопки зв'язку. У проданих авто є статус «Продано», кнопка «Підібрати схоже» і блок «Схожі автомобілі» (§16) |
| `/rezar-group/404.html` | сторінка 404 з кількома живими авто в наявності |

Фільтри каталогу записуються в URL (`?make=BMW&model=X5&year_from=2020&price_to=40000&km_to=90000&section=new&sort=price_asc`),
тож будь-яким станом каталогу можна поділитися посиланням.

## Що змоковано і що робитиме справжній бекенд

Архітектура за ТЗ (§2, §17–19): **API постачальника → сервіс синхронізації Rezar → PostgreSQL Rezar → API сайту → сайт**
(і в майбутньому Telegram Mini App на тому ж API). Браузер ніколи не звертається до API постачальника, а ключ API
зберігається лише на сервері.

| | у демо | у продакшені |
|---|---|---|
| **Дані авто** | статичні JSON у `public/data/`, які генерує `scripts/gen-data.mjs`: `catalog.json` (поля карток і фільтрів усіх 1200 авто), `first.json` (перша сторінка каталогу за замовчуванням), `cars/<n>.json` (деталі блоками по 100), `meta.json` (час синхронізації, лічильники, марки й моделі) | **PostgreSQL на Hetzner VPS** (Німеччина, стартово 4 vCPU / 8 ГБ / NVMe 80–160 ГБ). Індекси під фільтри й сортування, keyset-пагінація. Каталог масштабується до 10 000 авто без зміни фронтенду |
| **API сайту** | `src/lib/api.js` фільтрує, сортує й ділить на сторінки в браузері | ті самі функції стають HTTP-запитами (див. таблицю нижче), вся логіка переходить на сервер |
| **Синхронізація** | дати публікацій розкладені по слотах 08:00 / 20:00 за Києвом за останні 90 днів | **сервіс синхронізації**: 2 рази на добу о 08:00 і 20:00 Europe/Kyiv (з урахуванням переходу на літній час), вебхуки, якщо постачальник їх дає, щоденна повна звірка, ручний запуск адміністратором, журнал оновлень і помилок, сповіщення про збої. Нові авто публікуються автоматично, ціни й статуси оновлюються без підтвердження |
| **Ціна** | на сайт потрапляє тільки підсумкова `price`. Ціна постачальника й націнка лежать окремо в `mock-db/internal.json`, який не деплоїться | у БД зберігаються окремо `api_price`, `markup` (500 USD) і підсумкова ціна. API сайту віддає тільки підсумкову |
| **Повторне надходження** | 17 авто «продавались раніше»: той самий id, нова дата публікації (тому знову потрапляють у «Нові надходження»). Внутрішній тег та історія лежать тільки в `mock-db/internal.json` | без дубля: історія зберігається, ставиться внутрішній непублічний тег «раніше продавалась», нова дата першої публікації Rezar. Звичайна синхронізація цю дату не змінює (§4, §5) |
| **Фото** | Unsplash CDN (`auto=format` віддає AVIF/WebP, `w`/`h` задають адаптивні розміри). Вся логіка URL зібрана в одному файлі, `src/lib/photo.js` | **Cloudflare R2 + CDN**: фото скачуються тільки при додаванні або зміні, нарізаються у варіанти WebP/AVIF. Змінюється тільки `photoUrl()` у `src/lib/photo.js` |
| **Резервні копії** | — | **AWS S3**: щоденні зашифровані копії PostgreSQL, зберігання 30 днів, обмежений доступ, моніторинг успішності, періодична перевірка відновлення |
| **Моніторинг** | — | доступність VPS, CPU/RAM/диск, помилки синхронізації, автоматичні оновлення безпеки ОС і PostgreSQL |
| **Збій API постачальника** | `?sync=stale` | сайт працює з власної БД, показує час останньої успішної синхронізації і не стверджує, що застаріла наявність підтверджена |
| **Обрані** | `localStorage` браузера | так само (або акаунт / Telegram Mini App, коли визначиться поведінка, §15) |
| **Аналітика кліків** | події `rezar_call` / `rezar_message` / `rezar_car_view` / `rezar_favorite_add` … пишуться у `window.dataLayer` (`src/lib/track.js`) | той самий `dataLayer` підключається до GTM / GA4 |

Відповідність функцій `api.js` майбутнім ендпоінтам:

| `src/lib/api.js` | ендпоінт бекенду (пропозиція) |
|---|---|
| `api.query(filters, { cursor, limit: 24 })` → `{ items, nextCursor, total }` | `GET /api/cars?make=&model=&year_from=&…&section=&sort=&cursor=&limit=24` |
| `api.facets(filters)` → лічильники розділів, марки, моделі, діапазони | `GET /api/cars/facets?…` |
| `api.getCar(id)` → авто з деталями | `GET /api/cars/:id` |
| `api.similar(id, { cursor, limit: 12 })` | `GET /api/cars/:id/similar?cursor=&limit=12` |
| `api.byIds(ids)` (обрані) | `GET /api/cars?ids=…` |
| `api.meta()` → `{ lastSyncAt, stale, counts, makes, ranges }` | `GET /api/meta` |

Пагінація курсорна (keyset): курсор кодує ключ сортування останньої картки, тому сторінки не дублюються і не
пропускають авто, навіть якщо між запитами каталог змінився. Порядок стабільний, бо при однакових значеннях
сортування вирішує id.

## Як реалізовано «Схожі автомобілі» (§16)

Код у `src/lib/similar.js` (чисті функції, покриті `npm run check`). Довідник «аналогічного класу» лежить у
`src/lib/classes.js`: кожна пара марка + модель має клас (міський B, компактний C, середній D, преміум компактний,
преміум бізнес E, представницький, кросовери за розміром, позашляховики, преміум SUV, спорткари, пікапи).

1. **Кандидати**: тільки статуси «В наявності» й «В дорозі». Продані не беруть участі ніколи, як і саме вихідне авто.
2. **Відсікання**: ціна відрізняється від вихідної більш ніж на ±20 % або рік більш ніж на ±2 роки — кандидат
   відпадає. Порівнюються відображувані ціни Rezar у USD (API + 500). Пробіг не враховується.
3. **Три рівні, які не змішуються**:
   1) та сама марка і модель;
   2) інша модель тієї самої марки й того самого класу;
   3) інша марка того самого класу і бюджету (бюджет — це те саме вікно ±20 %).
   Спочатку показується весь рівень 1, далі рівень 2, потім рівень 3.
4. **Бали (максимум 100)**, за якими сортується всередині рівня:
   * марка / модель: 40 (повний збіг), 25 (інша модель тієї ж марки й класу), 10 (інша марка того ж класу);
   * ціна: 25 (відхилення 0–3 %), 20 (>3–5 %), 15 (>5–10 %), 10 (>10–15 %), 0 (>15–20 %);
   * рік: 25 (збіг), 20 (±1), 15 (±2);
   * паливо: 5 (те саме), 2 (споріднене: бензин↔газ, бензин↔гібрид, гібрид↔plug-in), 0 (інше);
   * силова установка, до 5: для двигунів внутрішнього згоряння за різницею об'єму (≤0.1 л → 5, ≤0.3 → 4, ≤0.5 → 3,
     ≤0.8 → 2, ≤1.2 → 1). Для електромобілів об'єм ДВС не використовується: два електромобілі дають 5, електро проти ДВС — 0.
5. **Порядок**: рівень ↑ → бали ↓ → відхилення ціни ↑ → різниця років ↑ → id ↑. Він повністю детермінований.
6. **Показ**: під повною карткою проданого авто йде тонка лінія, заголовок «Схожі автомобілі» і сітка
   (3 колонки на десктопі, 2 на телефоні). Порції по 12 з курсором, наступна порція завантажується заздалегідь,
   фото lazy. Якщо кандидатів менше 12, показується фактична кількість. Якщо їх немає зовсім, блок прихований,
   а «Підібрати схоже» веде в каталог на ту саму марку. Рекомендації рахуються з актуальних статусів і цін,
   тому після синхронізації оновлюються самі.

У ТЗ є суперечність: §4 каже «на сторінках проданих немає блоку схожих», а §16 детально описує цей блок саме на
сторінці проданого авто. Демо виконує §16 (на сторінках авто в наявності й у дорозі блоку немає). Це варто
підтвердити із замовником.

## Продуктивність

Після першого рендеру підвантажується тільки потрібне. Головне фото кожної сторінки (LCP) починає завантажуватися
з inline-скрипта в `<head>`, ще до запуску JS-модулів. Перша сторінка каталогу приходить окремим маленьким
`first.json` (24 авто, як відповідь справжнього API), а картка авто рендериться з власного блоку деталей і не чекає
весь каталог. Решта фото завантажуються lazy через `srcset`/`sizes`. Анімації (GSAP + ScrollTrigger + Lenis)
вимикаються при `prefers-reduced-motion` і спрощуються на слабких пристроях.

Мобільний LCP на production-збірці (Chromium, мережа ~1.6 Мбіт/с із затримкою 150 мс, CPU уповільнений у 4 рази,
кеш вимкнено): головна ≈ 1.4–1.6 с, каталог ≈ 1.5–2.4 с, картка авто ≈ 1.6–1.8 с. Ціль ТЗ — ≤ 2.5 с. Остаточні
цифри треба зняти на бойовому хостингу й CDN. Навантажувальні тести бекенду (§20–21) проводяться на реальному сервері.

## Структура

```
index.html, catalog/, car/, 404.html   сторінки (Vite multi-page); спільні частини в src/partials/
src/lib/        api (мок бекенду), similar + classes (§16), relTime + kyiv (§9), card, state (повернення назад), photo, format, favorites, track, contacts
src/pages/      код сторінок: home/, catalog/, car/
src/core/       boot, tier (рівень пристрою), scroll (Lenis + ScrollTrigger)
src/motion/     reveal, hero, parallax, count, accordion
src/styles/     tokens (кольори, тони секцій, сітка, типографіка), base, layout, components, motion + стилі сторінок
scripts/        gen-data (мок-дані), photo-catalog (перевірені фото), check-logic (тести), gen-logo
public/data/    те, що віддається браузеру
mock-db/        «внутрішня» частина бази (ціна постачальника, націнка, історія, теги); не деплоїться
docs/           BUILD_NOTES.md (технічні нотатки) і shots/ (скриншоти QA)
```

Дизайн-система: шрифти Fixel Display / Fixel Text (OFL, self-hosted), графітово-чорні, сірі й білі тони секцій,
лаймовий акцент тільки для головної дії та позначок «ви тут», радіуси 12–28 px, без тіней для розділення.
Детальніше в `docs/BUILD_NOTES.md`.
